# OpenAI-Compatible TTS Endpoints

Use this workflow when Hermes TTS should call a self-hosted or third-party service that implements the OpenAI speech endpoint.

## Procedure

1. **Check Hermes' actual provider contract.** Read the current config reference and implementation/docs for the installed version. Confirm the OpenAI TTS provider accepts a configurable `base_url`, which endpoint path it appends, how it sends the model/voice/format, and which API-key setting it reads. Do not infer compatibility from an OpenAI-shaped URL alone.
2. **Check the engine and all model components' terms before installing.** Verify the weights, tokenizer, vocoder, and any auto-downloaded dependencies independently. Match the license to the intended use; a non-commercial model is not suitable for monetized production. Do not assume a dependency is separately installable just because the server names it; inspect the server's documented install flow and logs, then let supported inference-time dependency loading handle it if that is the intended design.
3. **Prove the service locally on its host.** Check service health, then issue a real speech request to its documented endpoint. Confirm a successful status, non-empty audio bytes, and a decodable expected format. A green health endpoint alone does not prove inference works.
4. **Prove client-to-host reachability before changing network policy.** From the Hermes client, test the exact service port and inspect the route. If useful, capture packets at the service host while making a client request. SSH access proves only that SSH is reachable; it does not prove arbitrary TCP ports pass. Conversely, a firewall allow rule does not prove packets reach that host. Do not change firewalls or tailnet ACLs until evidence locates the drop.
5. **If SSH works but the service port is not reachable, use a narrow local forward.** Run an SSH local forward bound to `127.0.0.1`, mapping one local port to the service's loopback port on the host. For a persistent desktop setup, use a systemd user unit with `BatchMode=yes`, `ExitOnForwardFailure=yes`, keepalives, `Restart=always`, and a short `RestartSec`; enable it for the user's default target. Use the existing SSH identity/host verification. Do not place passwords or tokens in the unit or command line. Test the local forwarded health endpoint before changing Hermes config.
6. **Configure minimally and verify the write safely.** Back up the existing config, change only the relevant TTS provider/base URL/model/auth fields, and read back those exact fields without printing unrelated config that may contain secrets. Use the endpoint appropriate to the actual route: remote host URL for direct connectivity, or `http://127.0.0.1:<forwarded-port>/v1` for a local SSH tunnel.
7. **Verify both integration layers separately.** First send a real speech request through the final client URL and validate the returned audio. Then restart/reload Hermes only as required by its config-loading behavior and exercise its actual voice/TTS path. Report API verification and Hermes voice-mode verification as separate results; never claim the latter from a successful standalone HTTP request.

## Pitfalls

- When authorization is **existing cached model only**, a cold HTTP speech request is not a safe cache probe: the server can fetch weights/tokenizers or auto-repair them. Check the service's effective cache location (not merely the conventional Hugging Face cache), transitive dependencies and loading code first. Setting offline flags on the HTTP client does not constrain the already-running server. If needed, use a bounded isolated invocation of the same installed engine with supported offline flags set before imports; stop on any missing component rather than restarting/reconfiguring the service or retrying online. Report isolated-engine success separately from HTTP/Hermes voice-mode acceptance.
- Treat Tailscale peer `Online` metadata as advisory: a false value does not override a successful authenticated SSH connection. Verify the exact route/port before declaring a host unavailable.

- Prefer a narrow SSH forward over broad firewall/ACL changes when the service is loopback-bound and SSH is already an approved reachable path; this avoids exposing an inference port and limits network changes.
- Do not conclude the tailnet ACL is the cause from a timeout alone; compare the client route, a known-working port, and host-side packet capture because routing, filtering, and service binding produce different evidence.
- Do not claim an installed TTS setup is usable until a real inference request returns valid audio; first-time model/dependency loading can make the first request slower than later requests.
- Do not treat endpoint success as commercial clearance; model and dependency licenses govern the intended downstream use.
